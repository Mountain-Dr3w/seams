In my last post, I wrote about the design artifacts I stopped making once I could build software myself. The ones I still use have changed too. I spend more time writing down things I used to assume the reader already knew.

We still have user stories, design docs, acceptance criteria, architecture decision records, README files, component specs, and coding standards. Teammates read them, but so do the models we use to write code and pick up tasks. It's tempting to assume those models can just use the documents we already have. That gets harder when a ticket depends on conversations that never made it onto the page.

A lot of project documents worked because people filled in the missing context. A ticket could be vague because the engineer knew the codebase. Acceptance criteria could leave something out because the PM and designer had already talked it through. "Follow the existing pattern" could be enough for a teammate who'd worked on that pattern last week. None of that was especially good practice, but we often got away with it.

A model working from the ticket doesn't have that conversation. If a constraint only lives in someone's head or a Slack thread it hasn't seen, it may produce code that looks reasonable and still misses what the team intended. I've spent enough time correcting that code to be more careful about what I leave out.

## the standard went up

I don't think we need a whole new set of documents, although I'd be interested to hear what other people are trying. User stories, component specs, decision records, and coding standards still have uses. I need mine to include enough context that someone can work from them without already knowing the project.

That doesn't mean making everything longer. I want to be able to find the problem, the constraints, the patterns to follow, and the decisions we've already made. A long explanation that leaves those things vague still leaves me cleaning up the same mistakes.

In Velveteen, the best example is STANDARDS.md. I built Velveteen to generate a coding standards file for each project based on the patterns in its codebase. I'd describe a feature to Claude, get code that worked but didn't match the conventions already in the project, and then spend time cleaning up the inconsistencies. I hadn't written down those conventions or made sure the model had seen examples of them. Telling it to "use the existing style" wasn't doing much.

STANDARDS.md records naming, file structure, import conventions, environment variable handling, security basics, and error-handling patterns. That gives the next coding session a place to start. Often it's just me coming back five minutes later, asking for the next feature without wanting to explain the project again.

## where it shows up most

User stories and acceptance criteria are where I run into this most often. A ticket that says "add export feature" might be enough to start a conversation with an engineer after standup. As an instruction to a coding model, it leaves a lot open. Which format should the export use? Where does the user start it? Who has permission? What happens with a large dataset, and what does the user see while it runs or if it fails?

I'd want those answers before an engineer built it too. We just might have worked them out in conversation and never updated the ticket. When I'm both writing the story and building from it, it's especially annoying to watch the model guess at something I knew but didn't bother writing down.

The same problem shows up in other documents. An architecture decision record needs to explain why we made a choice so the next person, or model, doesn't suggest undoing it without that context. A component spec needs the loading, empty, disabled, error, and partial-success states. Leaving those out means someone has to make them up during implementation.

## artifacts as shared memory

When project knowledge is spread across Slack threads and private conversations with coding models, I keep having to explain decisions again. A new contributor has to ask around. A new coding session starts without something I explained in the last one. The work gets done, but we're spending time recovering things we already knew.

Keeping those decisions in project documents helps, as long as we keep the documents current and actually use them. A standards file the model never reads won't fix inconsistent code. A decision record that no longer matches the implementation can create a different kind of confusion.

For my own projects, this has made me pay more attention to what I leave behind after a coding session. If I had to correct a convention or explain a constraint, I want it written somewhere I'll use next time. STANDARDS.md came out of getting tired of making the same corrections. That's been a more useful place to start than trying to write a perfect prompt.
